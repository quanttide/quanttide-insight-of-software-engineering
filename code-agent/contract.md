# 契约原型：角色 × 义务 × 保证 × 执行者

从两本 handbook（[code 手册](https://github.com/quanttide/quanttide-handbook-of-software-engineering)、[work 手册](https://github.com/quanttide/quanttide-handbook-of-knowledge-work)）与仓库里的 `.quanttide/*/contract.yaml` 捕捉到的共同形状。

## 一、现场的四类契约

| 契约 | 载体 | 谁被约束 | 保证怎么判 |
|---|---|---|---|
| **平台契约**（`categories/platform`） | code 手册 | 跨项目的组件角色（Provider/Studio/CLI） | 质量门禁给命令：dart format / flutter analyze、gofmt / go vet、rustfmt / clippy，本地从严与 CI 一致 |
| **产物规范**（`piece/artifact`） | work 手册 | 每件产物 | 六条共性规则 + 每件产物自己的验收 |
| **任务规范**（`process/task`） | work 手册 | 产物之间的流动 | 三段齐全、已登记画廊、未违反共性规则 |
| **工作流步骤判据**（`code-implement.yaml` 等） | work 档案 | 一次具体工作 | 每步 `criteria` 带执行者：rule 跑命令、agent 判、human 拍 |

外加机器可读的两个实例：`.quanttide/asset/contract.yaml`（资产组成：双轴分类 + audience: human/ai/engine）与 `.quanttide/docs/contract.yaml`（文档规范：标题层级、代码块语言必填、命名大小写）。

## 二、原型拆成四件套

**① 角色**——契约先声明它约束谁。产物规范约束“产物”、平台契约约束“组件角色”（Provider=Go、Studio=Flutter、CLI=Rust，**不以项目为转移**）、工作区规范约束“一次工作的边界”。

**② 义务**——必须做什么，可数、可列。三段式流动、单一去处、不留副本；桶命名 `{产品线}-{用途}`、IaC 目录 `manifests/terraform/`。

**③ 保证**——怎样算做到，且**必须可判**。门禁给的是命令而不是形容词；验收是“未犯常见错误：把 `gallery.md` 改成 `case.md`……”这种可对照的清单。

**④ 执行者**——每条义务与保证标出归属。工作流里这一步是显式的三类：`rule`（机器可运行）/ `agent`（AI 判）/ `human`（人拍）。**这就是“责任分配”在文本里的落地形式**。

## 三、契约约束的两种对象：结构与依赖

落到软件工程，契约要锁的东西只有两类——**模块结构**（东西怎么切、依赖往哪走）与**外部依赖**（引别人的还是自己造）。这两类恰是 AI 的弱项：它能写出跑得通的代码，却不会自然做出好的模块划分，也不会替你想清楚该不该引一个依赖。**所以它们必须是契约的显式条款，不能留给生成者临场决定。**

### 结构契约的第一个来源：借框架的家法

Flutter 项目一律要求按 Bloc 给的架构分层——**用框架的家法约束 AI 的模块化习惯**。`qtcloud-work/studio` 是这么落的：

- `lib/` 按 **Bloc 家法**重排：`repositories/`（接口 + 两套实现：命令行客户端与本地）、`states/`（Bloc）、`screens/`、`widgets/`（**应为 `views/`，见下方案例**）；`test/` 跟着分层
- 状态 + 事件 + Bloc 住 `states/`（`workbench_bloc.dart` 取代 `StatefulWidget` + `setState`），**界面件只认传进来的模型与回调**
- 干掉 `lib/models/`：界面与 Bloc 直接用工具箱的领域对象——目录里不留第二份模型

借家法比自己定抽象好，理由三条：

1. **AI 有语料**：主流框架的目录与分层是训练数据里的高频模式，遵守概率远高于自定抽象层——约束成本最低
2. **生态有判据**：框架自带的目录约定、测试范式（`bloc_test`）、lint 可直接当门禁，不用自己造检查
3. **不必发明抽象**：结构来自框架而非我们的偏好——符合“不发明抽象层、结构即真实”

于是结构契约的写法是**三层来源、优先级从高到低**：先借框架家法（目录分层 + 各层职责）→ 再用平台契约补框架不管的（角色语言、桶、域名、门禁）→ 未覆盖处由项目自定。

### 案例：借家法要连命名一起借（2026-09-12）

`qtcloud-work/studio` 按 Bloc 家法重排 `lib/`，界面件那一层却写成了 `widgets/`——**按 Bloc 惯例该叫 `views/`**。

偏离的代价不在功能，在**约束的传导**：`views/` 是 Bloc 家法里的公共名词（训练语料里的高频分层），AI 认得它、也认它背后的职责划分；`widgets/` 只是个泛称，AI 无从对照。命名一偏，家法就从“照着做”退回“要人再解释一遍”——借来的约束被打折。

**作为契约生长的反例记下**：借家法要连命名一起借。家法的价值在于它是人与 AI 都认得的**公共名词**；自造同义词，等于把公共名词换成私有名词，约束成本立刻回到自己定抽象那一档。

### 阶段条款：分层起步，聚合写实（2026-09-12）

目录组织分两阶段，**第一阶段不判违规**：

- **初期按层**：领域模型未定型，聚合边界未知——分层（transport / service / repository / model 一类）是**不假设业务边界的中性骨架**，能跑且不欠债；它又是框架与语言的默认（Bloc 家法、Go 五件套），借家法的三个好处在这一阶段全适用
- **成熟转聚合**：跑过一段后边界从实践长出，此时重组目录只是**把已存在的边界写实**，不是发明结构

**三个可数触发**（满足任一条就该转）：同一聚合的对象散落在 ≥3 个目录；改动清单里总是同一组文件一起出现（变化耦合）；「改这个功能要动哪些文件」答不出。

**转换纪律**：行为不变（同一批用例或对账脚本为证——照 toolkit 抽取的做法）；一次只转一个聚合、转完删旧文件不留副本；转换本身按任务写（目标/步骤/验收）。

**硬禁（唯一的违规形态）**：**同一目录不得同时混用「层名」与「聚合名」**。混用态既不是层也不是聚合——人无从推断改动范围，AI 更无从推断（它只认得公共名词）。这是契约的下界：不规定走哪一阶段，但规定不许停在说不清的地方。

**现状反例**：`qtcloud-work/studio` 处在第一阶段（`lib/` 按 Bloc 家法分层），本身不违规；但 `lib/repositories/local/` 里 `tasks.dart`、`workflows.dart` 是聚合名，`environment.dart`、`paths.dart`、`yaml.dart`、`prompts.dart`、`help.dart` 是职能名——**混用待清**：或按聚合重排，或明确归入职能子目录。

### 结构契约：现场已有的条款

| 条款 | 现场表述 | 出处 |
|---|---|---|
| 角色唯一 | 一个模块一件事：`transaction` 是账本写入唯一入口，`order` 是结算编排者 | qtcloud-pay index |
| 依赖单向 | 契约单向依赖：端侧（provider/cli/studio）引用工具库契约，**绝不反向定义**；契约演进由 fixtures 驱动 | qtcloud-pay models |
| 边界清晰 | 镜像边界：客户端模型与 provider API 的 JSON 形状一一对应（`fromJson`/`toJson` 全字段），无客户端派生逻辑 | qtcloud-execute studio |
| 能力刻意收窄 | 所有模型只有「发现、展示、分享」能力，没有写 OSS 的能力——这是刻意的边界 | qtcloud-asset provider |
| 平行不纠缠 | `channel` 刻意不依赖账本模块；支付成功不入账，闭环推迟 | qtcloud-pay index |
| 关联最少 | 应用层零关联表（ID 同源直连） | qtclass |
| 组装与实现分离 | `cmd/server` 组装，`internal/` 按模块分包（transport / service / repository / model / gorm 五件套） | qtcloud-pay index |
| 横切约束集中一处 | 横切设计约束沉淀在 `src/provider/docs/conventions.md`，全部模块遵守 | qtcloud-pay index |
| 按角色定语言 | Provider=Go、Studio=Flutter、CLI=Rust，不以项目为转移 | 平台契约 |

结构契约的共同点：**条款全是“谁不依赖谁”“谁只能做什么”**——它约束的是关系，不是内容。

### 依赖契约：现场已有的条款

| 条款 | 现场表述 | 出处 |
|---|---|---|
| 外部依赖先看官方 | 接入外部系统时先看有没有官方 SDK 等工具包——自己写重复量大、特别容易出错 | journal 2026-08-26 |
| 抽象一层的判据 | 多一层依赖换掉两份重复；值不值得由创始人定范围 | code-implement-toolkit |
| 抽出去必须发布 | **挂本地路径不算抽出去**：两侧依赖已发布版本号（crates.io / pub.dev），不是 path | code-implement-toolkit |
| 一条发布线一个语言包 | Rust 与 Dart 各自定版本、各自发，互不牵连 | code-implement-toolkit |
| 默认选型成文 | 框架、状态管理、路由、UI 有默认，项目未声明时遵循默认 | flutter 手册 |
| 外部依赖的坑写进契约 | CanvasKit 托管在 gstatic、国内不可达 → 构建时自托管；发布前须在无代理网络验证 | flutter 手册 |

依赖契约的共同点：**管的是“引谁”和“怎么引才作数”**——作数与否有硬标准（版本号 vs 本地路径）。

### 两处空白（待定）

- **家法没进手册**：框架手册现在只记“选型”（Bloc / go_router / Material），没记“家法”（目录分层与各层职责）——所以“按 Bloc 家法分层”这条约束只能靠人现场要求，AI 手上没有可照的文本。它该补进 code 手册的 frameworks 层，与选型并列
- **依赖契约没有许可清单**：没有一处列明“哪些外部依赖已被许可”。选型靠默认手册 + 临时判断，AI 每次都可能引一个新依赖进来

## 四、契约与规格的三条差别

**下界而非上界。** 平台契约明文：“**契约未覆盖的选型由项目自定**”“状态管理库（如 Riverpod）属项目内选型，不纳入平台契约”。规格倾向于描述可接受行为（什么可以），契约只锁定必须的（什么一定），未覆盖处留给对方。

**保证由独立方判。** 执行者不能自判：步骤由 AI 跑，判据里常由 rule 或 human 来判——判据的执行者与义务的执行者分离，契约才有约束力。

**有权威载体。** 每份契约住在唯一处：平台契约在 code 手册、产物契约在画廊案例、JSON 形状的权威在 toolkit `tests/fixtures/`、资产与文档契约在 `.quanttide/`。契约不许有第二个副本——否则判的时候不知道按哪份判。

## 五、契约怎么长

**从实践提炼，反例修正规则。** 平台契约“从现有应用的工程实践中提炼”；产物规范明写“新增产物的规格即对共性规则的检验，**出现反例时修正规则而非硬套**”。所以契约可修订，且触发条件是反例，不是偏好。

结构契约与依赖契约正是反例最集中的两处——AI 每次生成都可能悄悄多引一个依赖、或把本该单向的依赖接成双向。**这两类最该由人先写下条款**，等反例来修正。

## 六、与观察者的接口

契约就是观察者要的那个中间表示：**义务与保证分开列，人审的是契约而不是产物**。验证记录里那条「反馈循环缺失」在这里闭合——有判据（可跑的门禁、对账脚本、验收清单）就是循环闭合，只能靠事后返工发现就是缺失。所以“保证必须可判”不是文风要求，是观察者能不能成立的前提。
