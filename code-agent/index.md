# 编程智能体：核心不是工作流，而是意图驱动 + 先跑通再治理

**预测**：把知识工作那套流程化范式套到编程上会失效——规范流程只能保证产出尽可能地靠近人类的理解范围，不能保证它写出来的东西科学合理。

**瓶颈不在生成，而在对齐**：AI 会发明我们不知道是什么的概念、结构和模型；人类脑中的模型又未必正确。于是需要把「人类意图模型」和「AI 实际建的模型」进行对比，甚至反过来先写代码、后治理。这会带来巨大的理解负担——它不是靠串联工作流能解决的，所以工作流不再是产品核心，至少不是交互核心。这一点与知识工作不同：知识工作处理大量琐碎的碎片，流程有效。

**优先级**：纠正很重要，但首先要保证的是能用；从「能用」到「好用」之间还有一段距离，需要控制这段距离。

**两个单元**：

1. 生成器——自由探索、建模、实现，先保证系统能跑
2. 对齐机制——解释、映射、对比、重构理解，把 AI 的隐式模型外化成人类可审查、可干预的结构

**架构**：探索者-观察者。其中观察者需要专门设计，是当前最缺的一侧。

**产品形态**：内置一套 harness 机制——上层交互极简、符合直觉，复杂性全部放进 harness 骨架，由骨架驱动内部单元合理分工。据此构建的编程智能体，是更高层次的、专门用来做复杂系统构建的智能体，追求高一致性。基准线取 PI + DeepSeek-V4.1：以它的行为作为基准去考虑怎么做，才比较科学合理。

**现状与摩擦**：现在的「实验室 + 平台 + 工具库」范式勉强够用，但摩擦很大、很低效；摩擦点主要就在对齐——能用，但对齐起来非常困难。

**待解问题**：对齐的对象是什么（行为、结构、意图、约束，还是演化历史）；如何把 AI 发明的概念转成人类可审查的中间表示；「能用」与「好用」之间如何度量、由谁判定；harness 的边界在哪（哪些放骨架、哪些放具体单元）；人类意图建模如何不成为瓶颈（是否允许 AI 反向提出新意图模型）；以 PI + DeepSeek-V4.1 为基准线时，要对比哪些行为指标（一致性、可解释性、重构成本、对齐耗时）。

**可测形式（2026-09-12 验证收窄）**：对齐困难可落成一个可数的状态——**反馈循环缺失**：交付时不知道它对不对（有判据=循环闭合；要靠事后返工才发现=循环缺失）。用例设计是让循环闭合的手段（案例库→用例）。

**已有雏形**：现有体系里已有一条对齐原则——**「AI 建议 + 人确认」，AI 不直接修改（判断不是事实）**。这是观察者的最小形态。所以观察者不是全无，而是只有雏形、没有专门设计。

**边界**：这套结构在更复杂、更大体量的知识工作中也会用得到；但编程与知识工作的分野要守住——流程化适用于碎片处理，不适用于复杂系统构建。

## 验证记录

**2026-09-12 首次验证（零成本，翻存量证据）**：证据取 `journal/qtcloud-course/2026-08-27.md`（一手自述），旁证取 `profile/` 全库的对齐词汇密度。

| 断言 | 证据 | 判定 |
|---|---|---|
| 瓶颈不在生成，在对齐 | 「团队层面的生产效率有很大一部分还是幻觉，很多关键且非常精密的调整，还是需要我自己来动」 | 支持 |
| AI 建的模型与业务对不上 | 「团队层面对于字段级别的建模明显不足，这会直接影响最终的业务效果」 | 支持 |
| 人类自己的模型未必对 | **「我建的模型，我不知道对于真实业务可不可靠」** | 支持（最强） |
| 单向对齐不成立，需对比 | 由上条直接推论：连人的模型都不确定，「先定意图模型再写代码」无从落脚 | 收窄后支持 |
| 工作流不是核心 | 团队规模化产出仍是幻觉；工程标准这类流程性文件靠换更聪明的模型而非改流程 | 弱支持（旁证） |

旁证：`profile/` 里「对齐」是反复出现的动作甚至工作阶段——「v0.1.0 对齐阶段」「镜像边界清晰」「契约与实现对齐」「契约权威在 toolkit tests/fixtures」。按词频即成本的逻辑，对齐是持续消耗最大的一处。
